## Design Specificity Verdict

**Split verdict: the content layer is genuinely authored for film-set AD coordination; the visual/interaction shell is generic dashboard-interchangeable.**

The vocabulary and data model are real and specific — 1st AD / 2nd AD / Key Costumer / Sound Mixer / Gaffer, a correct department taxonomy, real gear (Arri SkyPanel S60, a Condor, a rain tower), real lens/exposure language (32mm T2.0, f/2.8 equivalent, 2:1 ratio, rack focus), a real take-result taxonomy (print / hold / noGood / incomplete), and a correctly-ordered day frame (call time → first shot → wrap target). This isn't a reskinned to-do app — someone who has worked a set wrote this copy.

But strip the words and the shell — dark 240px icon+label sidebar, teal-accent cards, uppercase-label pill badges, off-white canvas — is identical to any B2B SaaS ops dashboard. Nothing in typography, motion, or composition is structurally specific to a physical, urgent film set. The one place this could have shown up — the nav/role chrome (`Layout.tsx`, `RoleSwitcher.tsx`) — is the most generic part of the app: a plain dropdown list of role names with no visual identity per department. Domain fluency lives in the copy, not the design language.

## Overall Impression

On Cue's writing and data model know exactly what a 1st AD's day looks like. Its interaction layer doesn't know whether it worked. The single biggest opportunity is closing that gap: right now, the two moments the whole premise depends on — a department declaring itself ready, and the 1st AD clearing the hold — either give no visible confirmation or (in Clear Hold's case) lead nowhere, since the `'rolling'` state it's supposed to trigger is never set anywhere in the app. A tool whose entire pitch is "everyone always knows the current state" currently can't tell its own users their click registered.

## What's Working

1. **Domain-authentic copy and data model.** The vocabulary, gear, and workflow order throughout `seed.ts` and every page read like they came from someone who's actually worked a set, not a generic ops template with labels swapped in.
2. **A restrained, consistent visual system.** The color-token/card/pill/button system in `index.css` is applied faithfully everywhere, producing a calm, professional read that suits high-stress subject matter well — the strongest-scoring heuristic (Aesthetic and Minimalist Design, 3/4).
3. **Real per-role content differentiation on My Set.** Each of the eight roles sees genuinely different action text, detail, and target time on the same screen — a concrete, well-executed demonstration of the product's core premise, not just a filtered list.

## Priority Issues

**[P0] Declaring yourself "ready" gives no visible confirmation at the exact moment it matters most.**
- **Why it matters**: This is the single highest-stakes beat in the whole app — a Gaffer or Wardrobe person marking themselves ready under time pressure. The clicked button keeps the same label and enabled state; nothing checks, disables, or confirms. In a real use case a user can't tell the click registered and will re-click or double-check over radio, undermining the tool's entire reason to exist.
- **Fix**: Give the clicked "ready" button an immediate inline confirmed/disabled state, in addition to updating the shared app state other pages read.
- **Suggested command**: `/impeccable polish` (Lighting Console, Wardrobe & Talent, My Set's Gaffer/Wardrobe/Talent-Assistant action buttons)

**[P0] Most action buttons across the app are decorative, and indistinguishable from the ones that work.**
- **Why it matters**: The large majority of role-action buttons (Need 5 Minutes, Equipment Issue, Print, Hold, No Good, Go Again, Move On, Escalate, Send 5-Min Check-in, Reorder Next Setup...) are unwired no-ops styled identically to the two or three buttons that actually do something. For a tool meant to coordinate real people under pressure, an "Escalate Blocker" button that silently does nothing is a trust failure, not a cosmetic one.
- **Fix**: Wire the highest-traffic actions minimally, or visually mark unimplemented affordances so the interactive surface is honest about what's real in this prototype.
- **Suggested command**: `/impeccable harden`

**[P1] The app's own promised core feature doesn't exist in the build.**
- **Why it matters**: The README's "Core demo path" step 6 says "Open Agent Activity to see event routing and authorization decisions" — the feature that would demonstrate the product's core differentiator (role-based authorization and event routing). It doesn't exist: no matching file in `src/pages/`, no route in `App.tsx`'s `Page` type, zero matches for "agent" anywhere in `App.tsx`, zero matches for "Agent Activity" anywhere in `src/` (confirmed by grep, not just missing UI). Anyone following the product's own script hits a dead end on its central claim.
- **Fix**: Either build a minimal event log surfaced from the ready/hold state changes that already exist, or correct the README so the shipped demo matches its own script.
- **Suggested command**: `/impeccable shape`

**[P1] AD Command's readiness dashboard shows contradictory, stale numbers right next to the live status banner.**
- **Why it matters**: "Current Hold: 7 min" and "Next Scene Risk: +12 min late" are static JSX unconnected to `holdState`. Once hold clears and the big banner switches to READY, these two stat tiles keep showing the old numbers — contradictory status next to a cleared banner erodes trust in exactly the screen meant to be the single source of truth for a live, high-stakes decision.
- **Fix**: Derive both values from the same state driving the banner, or hide/relabel them once hold clears.
- **Suggested command**: `/impeccable polish` (AD Command)

**[P1] The safety-relevant equipment checklist doesn't gate the "ready" signal sitting right next to it.**
- **Why it matters**: Lighting Console's checklist — including "Fire extinguisher at generator" — is plain, uncontrolled checkboxes with zero relationship to the "Lighting Ready" button directly above it. A Gaffer can declare lighting ready without checking a single item, modeling exactly the "looked done, wasn't done" gap that causes real on-set delays and safety incidents.
- **Fix**: Require checklist completion (or an explicit override with a reason) before "Lighting Ready" is enabled.
- **Suggested command**: `/impeccable harden`

## Persona Red Flags

**Alex (Impatient Power User — a 1st AD/DP who's used similar coordination tools)**
- No keyboard shortcuts anywhere; switching roles requires a mouse-driven dropdown with no hotkey.
- No bulk actions across AD Command's 7-department grid; the one global "Send 5-Min Check-in" button is a no-op.
- Alex's highest-value action, "Escalate," does nothing, on both My Set and AD Command.
- Onboarding forces a ~2-3 second canned progress animation with no skip button before reaching the app at all.

**Jordan (Confused First-Timer — a newer Talent Assistant or PA)**
- Heavy unexplained jargon (T2.0, f/2.8 equivalent, 2:1 ratio, slate 42-14B) with zero inline help — the `.tooltip` class exists in `index.css` but is never used anywhere in the app.
- After clicking "Actor Ready" / "Lighting Ready," nothing confirms it — Jordan is left guessing whether the click worked (same gap as Priority Issue #1).
- Onboarding's "Upload Call Sheet" and "Import Production Schedule" cards show upload icons and "PDF, Excel, or CSV" copy but contain no actual file input — clicking either just runs the same canned animation as the fictional-template option, a silent bait-and-switch for anyone trying to import something real.

**Rico (project-specific — on-set crew mid-task, derived from the README's own framing of a user checking a device between physical tasks under time pressure, needing only "what's needed for the current setup and next camera roll")**
- My Set stacks four full info blocks (NOW / YOUR ACTION / WHAT CHANGED / UP NEXT) in one continuous scroll — Rico, glancing for 3-5 seconds, has to scroll past status and history to reach his actual action, when it should be the first thing visible.
- The only "something changed" cue is a static red dot on the nav item when on hold — it can't distinguish "new blocker since you last looked" from "still the same old blocker."
- Buttons use 10px/18px padding, well under the 44×44pt touch-target minimum recommended for on-the-move, possibly-gloved use.
- All app state lives only in React's in-memory state — a reload on spotty set wifi silently loses every marked-ready flag and role selection with no warning.

## Minor Observations

- Sidebar nav has 6 top-level items, just over the ≤5 working-memory guideline.
- The role-switcher dropdown has no outside-click-to-close handler — it only closes on explicit selection.
- "Reset Demo" sits directly under the role switcher with equal visual weight and no confirmation, despite being fully destructive.
- `--text-muted` is used for meaningful small print (timestamps, ETAs) on the app's off-white background throughout the app — contrast is likely under WCAG AA at these sizes (a known, systemic characteristic across every page, not unique to any one).
- Modeled-but-never-rendered data, confirmed by grep: `Setup.currentState` (the real ready/hold/rolling state instead lives in a disconnected, separately-declared `App.tsx` state variable), `Production.currentTime`, `CharacterLook.fittingStatus`, and `Take.causes`' structured arrays (only ever shown as prose in `take.notes`, never as the same cause-chip UI Live Take already built for its own selector).
- Six CSS classes are fully defined in `index.css` and never used anywhere: `.btn-amber`, `.btn-ghost`, `.tooltip` (+ its pseudo-elements), `.animate-fade-in`, `.animate-slide-in`, `.animate-pulse-amber`.
- `role="status" aria-live="polite"` appears on exactly one element in the whole app (AD Command's status card); My Set's equally state-critical HOLD/READY pill gets no equivalent treatment.
- Tailwind's `@tailwind` directives are imported in `index.css` but the app is built almost entirely with inline styles plus a handful of hand-rolled classes — dead configuration, not an active part of the system.

## Questions to Consider

- If "Agent Activity" is the feature meant to prove the product's core premise, is its absence an oversight, or a sign the routing/authorization model itself was never fully worked out?
- Any role can currently navigate to any page — if role-based access really is the differentiator, shouldn't the nav itself change per role the way My Set's content already does?
- What would it feel like to mark yourself "ready" on a real set and get zero acknowledgment? Would you trust the tool the second time?
- Given how much of the button surface is decorative, what's the actual boundary of this prototype — one fully-wired path with everything else as visual reference? If so, shouldn't the unwired buttons look different so that boundary is honest?
